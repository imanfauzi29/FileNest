\# Feature 06 — Review Changes



\## 1. Overview



Review Changes is the central approval interface for all proposed filesystem operations generated by other application features.



It allows users to inspect, validate, approve, reject, or modify proposed changes before they are executed.



Changes may originate from:

\- Organization

\- Smart Rename

\- Duplicate Analysis

\- Approved Organization Rules

\- Approved Rename Rules



All filesystem mutations must pass through the backend Transaction Manager.



AI must never execute filesystem operations directly.



\### Goals



\- Provide a centralized approval workflow.

\- Display all proposed filesystem changes.

\- Allow users to inspect source and destination paths.

\- Identify validation errors and potential conflicts.

\- Allow users to approve, reject, or edit proposed operations.

\- Execute approved operations safely.

\- Maintain a complete audit trail.

\## 8. Approval Actions



Provide actions below the Change List.



\### Approve Selected



Approves the selected valid operations.



Behavior:

1\. Validate the selected operations.

2\. Ensure no unresolved conflicts exist.

3\. Update their status to Approved.

4\. Record approval information.

5\. Refresh the Change List.



Approval does not execute filesystem operations.



\### Reject Selected



Rejects selected pending operations.



Behavior:

1\. Request confirmation.

2\. Record the rejection.

3\. Update operation status to Rejected.

4\. Preserve the operation in History.



Rejected operations must not be executed.



\### Edit Selected



Allows users to modify supported operation details.



Examples:

\- Change destination path.

\- Change proposed file name.

\- Adjust folder destination.

\- Resolve supported conflicts.



After editing:

1\. Validate the updated operation.

2\. Recalculate affected destinations.

3\. Recheck collisions.

4\. Update the operation details.

5\. Return the operation to Pending Review if renewed approval is required.



Editing an approved operation must invalidate its previous approval.



\### Approve All



Approves all valid pending operations in the current scope.



Before approval:

\- Display the number of valid operations.

\- Display the number of operations excluded due to conflicts or validation errors.

\- Require user confirmation.



Approve All must never approve invalid or conflicting operations.



\## 9. Execute Approved



Execute Approved runs operations that have already received approval.



\### Execution Workflow



1\. User clicks Execute Approved.

2\. Display an execution confirmation dialog.

3\. Show the number and types of approved operations.

4\. Backend revalidates all operations.

5\. Transaction Manager creates an execution batch.

6\. Operations are executed safely.

7\. Execution status is persisted.

8\. Results are recorded in History.



\### Confirmation Dialog



Display:

\- Total approved operations

\- Move operations

\- Rename operations

\- Copy operations

\- Delete operations

\- Operations requiring additional validation



Provide:

\- Cancel

\- Execute Now



The confirmation must clearly explain that filesystem changes will occur.



\### Execution Rules



\- Only approved operations can execute.

\- Revalidate source and destination immediately before mutation.

\- Never silently overwrite existing files.

\- Detect stale plans and changed source files.

\- Skip operations that fail validation.

\- Record individual operation results.

\- Support best-effort rollback.

\- Preserve completed operation records even when a batch partially fails.



\### Execution Progress



Display:

\- Batch ID

\- Total Operations

\- Completed

\- Failed

\- Skipped

\- Current Operation

\- Progress Percentage

\- Started At

\- Elapsed Time



Supported statuses:

\- Queued

\- Running

\- Completed

\- Partially Completed

\- Failed

\- Cancelled



\## 10. Conflict Handling



Potential conflicts must be clearly visible.



Examples:

\- Destination file already exists.

\- Source file no longer exists.

\- Source file has changed since analysis.

\- Destination folder is unavailable.

\- Insufficient permissions.

\- Invalid destination path.

\- Duplicate destination names within the same batch.



\### Conflict Resolution



Depending on the operation, provide:

\- Choose Another Destination

\- Change File Name

\- Skip Operation

\- Reject Operation

\- Re-analyze



Never provide an automatic overwrite option.



After conflict resolution, validate the operation again.



Any material change to an approved operation requires renewed approval.



\## 11. Bulk Operations



Users may select multiple operations.



Supported bulk actions:

\- Approve Selected

\- Reject Selected

\- Execute Approved

\- Filter Selected

\- Export Change List



Bulk actions must operate only on eligible records.



For example:

\- Invalid operations cannot be approved.

\- Pending operations cannot be executed.

\- Rejected operations cannot be executed.

\- Already executed operations cannot be approved again.



Display a clear result when some selected operations cannot be processed.



\## 12. API Requirements



The API must support at least the following operations.



\### Get Changes



`GET /api/changes`



Query parameters:

\- status

\- action\_type

\- source

\- search

\- page

\- page\_size



Returns paginated change records.



\### Get Change Details



`GET /api/changes/{change\_id}`



Returns complete operation details and validation information.



\### Approve Changes



`POST /api/changes/approve`



Request:

\- change\_ids



Approves eligible operations.



\### Reject Changes



`POST /api/changes/reject`



Request:

\- change\_ids

\- reason



Rejects selected operations.



\### Update Change



`PATCH /api/changes/{change\_id}`



Updates supported operation details and triggers revalidation.



\### Validate Changes



`POST /api/changes/validate`



Request:

\- change\_ids



Revalidates selected operations.



\### Execute Approved Changes



`POST /api/changes/execute`



Request:

\- change\_ids or batch scope

\- confirmation



Creates an execution batch containing eligible approved operations.



\### Get Execution Status



`GET /api/changes/executions/{batch\_id}`



Returns execution progress and operation results.



\### Get Execution History



`GET /api/changes/executions`



Returns previous execution batches.



These endpoints are proposed API contracts. Adapt them to the existing backend conventions.

\## 14. Transaction Manager Requirements



The Transaction Manager is the only component allowed to perform filesystem mutations.



Responsibilities:

\- Validate operation scope.

\- Validate canonical source and destination paths.

\- Check source file state.

\- Detect destination collisions.

\- Execute move, rename, copy, create-folder, and approved deletion operations.

\- Persist operation results.

\- Handle partial failures.

\- Perform best-effort rollback.

\- Record audit information.



\### Operation Safety



\*\*Move\*\*

\- Same-volume moves must be validated before execution.

\- Cross-volume moves must use copy, verify, and delete only after explicit approval.

\- Never delete the source before destination verification.



\*\*Rename\*\*

\- Validate the resulting name.

\- Detect collisions.

\- Preserve extensions according to the approved plan.



\*\*Copy\*\*

\- Verify the destination.

\- Never overwrite existing files silently.



\*\*Delete\*\*

\- Use Windows Recycle Bin or an explicitly approved recoverable mechanism.

\- Never permanently delete automatically.



\*\*Create Folder\*\*

\- Validate the parent directory.

\- Check for existing folder names.

\- Never overwrite existing directories.



\## 15. Safety Constraints



\- Only registered Managed Folders may be modified.

\- AI must never execute filesystem operations.

\- Pending operations must not execute.

\- Rejected operations must not execute.

\- Invalid operations must not execute.

\- Approved operations must be revalidated before execution.

\- Any material operation change invalidates previous approval.

\- Never silently overwrite files.

\- Never permanently delete files automatically.

\- Never follow symbolic links, junctions, or reparse points by default.

\- All filesystem mutations must pass through the Transaction Manager.

\- Record all approvals, rejections, executions, and failures in History.

\- Preserve operation records for auditing.
